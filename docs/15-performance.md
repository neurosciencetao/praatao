# 15. 性能：让教练感觉不到等待

这一篇记录 Praatao 悬浮教练的一次性能改造：测量方法、改了什么、每个改动
为什么这么做、改造之后还剩下什么慢，以及所有数字的复现命令。

所有数字都在本机（Windows 11，Praat 6.4.12）上、用真实运行的 Praat 测得，
测量工具是 `prototypes/v1/experiments/perf_probe.py`。

---

## 1. 为什么要做这件事

悬浮教练的交互契约很简单：指针停在某个按钮上，卡片就出现。人的直觉是
"指针一停，说明就有了"，所以从指针停下到卡片出现之间，每多一毫秒都会被
读成"这个软件反应很慢"。

改造前，这条链路上有三件事会让人感觉"迟钝"：

1. **界面上有长时间卡顿**。指针在动的时候，界面线程会被占住几十毫秒，
   指针就"拖不动"，这是最难受的一种慢。
2. **等待时间由轮询节拍决定**。指针停下之后，教练要等下一个轮询周期，
   才知道"指针没有在动"。
3. **每一个空闲的周期都在做无用功**。空白的结果没有被缓存，树遍历在
   没有画布的时候照样每帧做一遍。

改造的目标不是把平均延迟压到某个漂亮的数字，而是：

* 指针在动的时候，界面线程永远不做超过 20 ms 的事；
* 指针停下之后，500 ms 内卡片一定在屏幕上（目标是 300 ms 左右）；
* 空闲时几乎不烧 CPU（省电，也让别的程序跑得动）。

---

## 2. 测量方法

### 2.1 工具

`prototypes/v1/experiments/perf_probe.py` 是一个独立脚本，它**启动真实的
教练进程**（`run.py`，真实的 Qt 卡片，真实的 Praat），并在其上打点：

| 测量项 | 方法 |
| --- | --- |
| 各个感知函数的单次开销 | 直接调用并计时，每个至少 20 次 |
| 端到端延迟 | 把指针放到按钮上，测到"卡片被画出来"为止 |
| 界面线程阻塞 | 测量鼠标轮询的实际间隔，与标称间隔的差 |
| CPU 占用 | 用 `psutil` 读教练进程的 CPU 时间，鼠标静止 20 s、移动 20 s |
| 误触发率 | 指针扫过一排按钮，每个停留 20 ms 到 320 ms，看卡片出现了几次 |

所有计时用 `time.perf_counter()`，报告**中位数**和 **p95**（不用平均值：
一次 500 ms 的卡顿会被平均值掩盖，却一定会被用户看见）。

### 2.2 一个关键设计：`--legacy`

只测"改完之后"没有意义，因为"改之前"是在几天前、在机器更忙的时候测的。
所以工具里有一个 `--legacy` 开关：它把**改造前的实现**装回运行时
（旧的命中测试、旧的���识库扫描、旧的画布查找、旧的菜单检查、旧的停顿
计时），然后用**同一套工具、同一台机器、同一段时间**再测一遍。

```bash
python prototypes/v1/experiments/perf_probe.py --legacy --out perf_before.json
python prototypes/v1/experiments/perf_probe.py            --out perf_after.json
```

两组数字因此可以直接相减。

### 2.3 防止别的程序干扰

测量期间别的程序移动鼠标，会让结果完全失真。工具会在每一轮前后检查
指针位置，被打断的轮次会被丢弃并报告出来（`disturbed_rounds`）。误触发
扫描同样会丢掉被干扰的访问。

## 3. 结果

### 3.1 总体

| 指标 | 改之前 | 改之后 | 变化 |
| --- | --- | --- | --- |
| 端到端延迟（中位数） | 380 ms | **312 ms** | −18 % |
| 端到端延迟（p95） | 498 ms | **336 ms** | −33 % |
| 端到端延迟（最大值） | 2635 ms | **346 ms** | −87 % |
| 轮询单次耗时（中位数 / p95） | 8.36 ms / 48.9 ms | **0.79 ms / 13.2 ms** | −91 % / −73 % |
| 界面线程单次阻塞（中位数 / p95） | 15.2 ms / 29.7 ms | **15.0 ms / 19.1 ms** | −1 % / −36 % |
| 指针静止时的 CPU | 14.8 %（一个核心） | **5.5 %** | −62 % |
| 指针移动时的 CPU | 11.5 % | **6.2 %** | −46 % |

### 3.2 端到端延迟的分解

| 阶段 | 改之前（中位数 / p95） | 改之后（中位数 / p95） |
| --- | --- | --- |
| 轮询节拍（tick_period） | 48.7 ms / 96.7 ms | 47.2 ms / 66.5 ms |
| 等待（停顿 + 轮询） | 373 ms / 491 ms | 299 ms / 327 ms |
| 命中测试（每次调用） | 8.26 ms / 16.0 ms | **0.002 ms** / 10.2 ms |
| 知识库查询 | 0.007 ms / 0.011 ms | 0.008 ms / 0.017 ms |
| 组织建议 | 0.094 ms / 0.166 ms | 0.103 ms / 0.220 ms |
| 卡片绘制 | 4.80 ms / 12.2 ms | 5.99 ms / 15.5 ms |
| 聚光灯 | 2.56 ms / 4.05 ms | 2.55 ms / 4.60 ms |
| 一次悬停的总工作量 | 7.47 ms / 14.7 ms | 8.71 ms / 20.1 ms |
| 最后一次轮询（画出卡片的那一次） | 16.2 ms / 181 ms | **7.3 ms / 16.3 ms** |
| 一次悬停里的命中测试次数 | 6.5 次 | 7.0 次 |

关键点：**等待**（停顿 + 轮询）占了端到端延迟的 95 % 以上，工作量本身
（不到 10 ms）几乎不重要。所以优化重点不是"把建议写快一点"，而是"别让
指针白等"和"别在界面上卡住"。

改之前的最大值 2635 ms 是一次意外：那一轮正好撞上深度探测的脚本在
Praat 里执行，所有对 Praat 窗口的读取都要排队。改之后同样的撞车概率
还在，但守卫让脚本更少发，最大值降到 346 ms。

### 3.3 各个感知函数的单次开销

| 函数 | 改之前（中位数 / p95） | 改之后（中位数 / p95） |
| --- | --- | --- |
| `uia.element_at_point`（按钮） | 6.33 ms / 8.16 ms | 6.25 ms / 8.48 ms |
| `uia.find_all`（整棵树） | 181.7 ms / 211.3 ms | 178.0 ms / 216.1 ms |
| `uia.tree`（Objects 窗口） | 81.1 ms / 195.4 ms | 85.6 ms / 121.3 ms |
| `uia.open_popup_items`（没有菜单） | 130.3 ms / 235.0 ms | **0.023 ms** / 0.024 ms |
| `uia.open_popup_items`（菜单开着，已缓存） | 30.5 ms / 37.1 ms | **0.099 ms** / 0.359 ms |
| `kb.lookup`（命中） | 0.002 ms / 0.002 ms | 0.007 ms / 0.008 ms |
| `kb.lookup`（落空，走全扫描） | 3.87 ms / 4.23 ms | **0.302 ms** / 0.358 ms |
| `probe.fast()`（UIA 读状态） | 32.1 ms / 214.8 ms | **2.03 ms** / 3.20 ms |
| `probe.quick()`（读窗口标题） | 0.46 ms / 0.57 ms | 0.47 ms / 0.73 ms |
| 菜单检查（`_menu_popup_open`） | 0.348 ms / 0.576 ms | **0.011 ms** / 0.012 ms |
| `canvas.capture`（抓屏） | 33.2 ms / 33.7 ms | 39.1 ms / 49.7 ms |
| `canvas.regions`（已缓存） | 0.000 ms | 0.000 ms |
| `probe.snapshot()`（深度探测，发脚本） | 273 ms / 311 ms | 295 ms / 328 ms |

几处需要说明的：

* `element_at_point`、`find_all`、`tree`、`canvas.capture` 这几行**没有
  改动**，两列的差别是测量噪声，不是改进也没有退步。它们是"还剩下什么
  慢"那一节的内容。
* 菜单检查那一行是单独测的（旧实现 `EnumWindows` 遍历桌面，新实现
  `FindWindowEx` 沿 `#32768` 窗口链找）：0.348 ms → 0.011 ms。
* 深度探测的脚本往返反而略慢（273 → 295 ms）：脚本发给 Praat 之后，
  Praat 要等自己的事件循环空闲才执行，这段时间跟机器的忙闲有关，
  两次测量之间差了 8 %，属于噪声范围。改造真正改变的是**发脚本的次数
  和时机**，不是单次往返的长度。

## 4. 做了什么，为什么

改动的文件：

| 文件 | 改了什么 |
| --- | --- |
| `run.py` | 命中测试缓存、停顿的计时起点、鼠标轮询记下指针最后移动的时刻、深度探测的空闲守卫 |
| `praatao/tutor/kb.py` | 知识库索引、归一化结果缓存 |
| `praatao/tutor/advisor.py` | 状态与状态探测器分开、悬停路径不许自己发探测脚本 |
| `praatao/sensors/uia.py` | 菜单检查走 `#32768` 窗口链、弹窗项从弹窗自己的树读、命名元素缓存的兜底 |
| `praatao/sensors/praat_state.py` | Objects 列表走窗口句柄、列表缓存、拒绝空脚本和目录 |
| `praatao/sensors/canvas.py` | 画布走 Win32 窗口树、空结果也缓存、慢路径只在新窗口出现时走 |
| `tests/test_performance.py` | 新增：索引等价性、命中测试缓存、停顿计时、传感器快捷路径 |
| `prototypes/v1/experiments/perf_probe.py` | 新增：测量工具（`--legacy` 可以测改造前的实现） |

### 4.1 空结果也要缓存（最大的一个）

`CanvasSensor.regions()` 原来的写法是：

```python
if not refresh and self._regions and (now - self._cached_at) < self.CACHE_TTL:
    return self._regions
```

`self._regions` 为**空列表**时，这个判断是假的，于是每一帧都要重新去找
画布。而找画布的兜底路径是遍历可及性树，**一次 90 ms**。

这个 bug 的杀伤力取决于状态：Praat 的 Picture 窗口开着的时候，快路径
（Win32 窗口树）能找到画布，一切正常；**Picture 窗口关着的时候**（也就是
只有 Objects 窗口开着，这是最常见的工作状态），每一帧都要走 90 ms 的树
遍历。实测：那一帧的耗时从 0.8 ms 涨到 **60.7 ms**，指针静止时的 CPU 也有
14.8 %，界面线程 90 ms 一次的停顿让指针"粘"在屏幕上。

改动：结果和"已经找过"这件事分别缓存（用时间戳而不是列表本身判断），
空结果照样缓存；兜底的慢路径只在**出现新的 Praat 窗口**时才会走
（新的窗口是新的画布的唯一来源）。

> 效果：轮询单次耗时 60.7 ms → **0.49 ms**（实测），指针静止时的 CPU
> 14.8 % → **5.5 %**。

### 4.2 命中测试加缓存

`uiautomation` 的 `ControlFromPoint` 一次要 6 到 10 ms。原来的代码**每
一次轮询都做一次**，而轮询每 45 ms 一次，也就是每秒 22 次。

改动（`run.py`）：

* 指针位置没有变，就复用上一次的结果；
* 指针动了，但仍在**同一个小的控件**里面（面积不超过 60000 平方像素），
  也复用：按钮不会在两次轮询之间长出另一个身份；
* 缓存有效期 1 秒；Praat 状态一变（对象变了）缓存作废。

> 效果：命中测试单次从 8.26 ms 降到 **0.002 ms**（绝大多数命中由缓存
> 直接回答）。一次悬停里的命中测试次数从 6.5 次变成 7.0 次（轮询跑得更
> 密了），但花在命中测试上的总时间从 54 ms 降到 **0.014 ms**。

### 4.3 停顿从"指针到达"开始算

原来停顿的计时起点是"轮询发现指针没动的那一刻"，所以实际停顿 =
标称停顿 + 0 到 45 ms 的轮询延迟。

改动：鼠标轮询（10 ms 一次）顺手记下指针最后移动的时刻；停顿从
`max(指针最后移动时刻, 上次卡片消失时刻)` 起算。效果是卡片出现的时刻
跟"指针真正停下来"对齐，而不是跟轮询节拍对齐。

### 4.4 停顿从 320 ms 降到 280 ms

这是唯一一处**调快了**的改动，明确记录在此。

改动的理由：既然计时起点对齐了指针的真实停留，280 ms 的停顿感觉上与
原来的 320 ms 一样（甚至更准），但卡片早 40 ms 出现。

误触发率的实测方法：指针从桌面空白处移到一排按钮上的某个按钮，停留
指定时间，再移开。每一次访问之前都先把卡片送走（否则上一张卡片可能盖住
下一个按钮，测的就不是教练了）。每一档 44 到 48 个控件访问，被别的程序
打断的访问会被剔除。

| 停留时间 | 改之前（停顿 320 ms，计时从轮询起算） | 改之前（停顿 280 ms） | 改之后（停顿 280 ms，计时从到达起算） |
| --- | --- | --- | --- |
| 20 ms | 0 % | 0 % | **0 %** |
| 40 ms | 0 % | 2.2 % | **0 %** |
| 60 ms | 0 % | 0 % | **0 %** |
| 100 ms | 0 % | 2.1 % | **0 %** |
| 150 ms | 0 % | 2.1 % | **0 %** |
| 200 ms | 0 % | 0 % | **0 %** |
| 240 ms | 0 % | 0 % | **0 %** |
| 280 ms | 4.4 % | 0 % | **0 %** |
| 320 ms | 0 % | 0 % | 33.3 % |

怎么读这张表：

* **停留不超过 280 ms，三个设置都是 0 % 误触发**。改之后的版本一点
  也没有变差。
* 320 ms 那一行的 33.3 % 不是"误触发变多"，而是计时语义变准了：改之后
  的停顿从"指针到达"起算 280 ms，所以停留 320 ms 当然会触发；改之前的
  停顿从"轮询发现指针没动"起算，等效停顿是 280 到 365 ms（取决于轮询
  的相位），停留 320 ms 常常刚好不够。
* 中间那一列出现的 2.1 % 是个别访问的噪声（48 次里 1 次），原因是那一
  次教练的轮询被拖住，指针在教练看来停留得比实测更久。

也就是说：**误触发率没有变差，触发时刻反而更符合"指针停了 280 ms"
这个直觉**。

### 4.5 知识库建索引

`KnowledgeBase.lookup()` 原来每次落空都要扫全部 288 条，并且对每一条的
关键词重新做归一化：3.87 ms（p95 4.23 ms）。

改动：知识库在构造时建三张索引，别名精确表、别名子串表（按长度排序）、
关键词表；每条知识的归一化结果算一次就缓存。

> 效果：落空查询 3.87 ms → **0.302 ms**（13 倍）。
> 等价性用 2756 次查询逐一比对旧实现验证过：结果完全一致。

### 4.6 菜单与弹窗走 Win32 快捷路径

* 判断"有没有菜单弹出"：原来用 `EnumWindows` 遍历桌面上约 800 个顶层
  窗口；改成用 `FindWindowEx` 沿 `#32768` 窗口链找（只有菜单才是这个类），
  并检查它是不是 Praat 拥有的。0.348 ms → 0.011 ms。
* 读取"菜单里有哪些项"：原来遍历每个 Praat 窗口的整棵树（130 ms），
  改成直接读弹窗窗口自己的控件树，并按弹窗句柄缓存。
  0.099 ms（命中缓存）/ 一次 13 ms（冷读）。
* **没有菜单开着的时候直接返回空**，不再白走一遍树。

### 4.7 状态探测走 Win32 句柄

`probe.fast()` 原来要先在整棵可及性树里找到 Objects 窗口的 ListBox
（32.1 ms，p95 214.8 ms）。改成先用 `FindWindow` 拿到 "Praat Objects"
窗口的句柄，再用 `EnumChildWindows` 在它的子窗口里找那个 `ListBox`，
最后用 `ControlFromHandle` 取它的可及性控件。列表内容另外缓存 5 秒，
因为列表本身很少变。

这里还有一个更细的坑：ListBox 在 Win32 这一层是 "form" 面板的子窗口，
**不是** Objects 窗口在可及性树里的直接子节点。所以按"直接子节点的
ClassName"去找会找不到，然后掉进兜底路径（整棵树搜索），冷启动要
**1.9 秒**。改成按窗口句柄找之后，冷启动是 83 ms，热启动 4 ms。

> 效果：32.1 ms → **2.03 ms**（热）；冷启动 1960 ms → **83 ms**。

### 4.8 深度探测（发脚本）更克制，并加了一道保险

深度探测用 `Praat.exe --send` 发脚本，它有两个代价：**会把菜单关掉**，以及
**会把 Praat 拉到前台**。改造后：

* 用户还在动鼠标或者刚敲过键盘时，脚本**不发**（用
  `GetLastInputInfo` 判断，1.5 秒内有过输入就等）；
* 菜单开着时不发；
* **Praat 不在前台时绝不发**（原有的 `praat_has_focus()` 守卫，保留）。

另外修掉一个真实的 bug：空的探测脚本以前会被当成"当前目录"发给 Praat，
Praat 弹出一个模态的 Message 框，之后所有对 Praat 窗口的读取都被卡住
（实测 `fast()` 慢到 2.4 到 3.6 秒）。现在空脚本和目录路径都会被拒绝。

### 4.9 建议里不再偷偷发脚本

`Advisor` 原来把"状态"和"状态探测器"放在同一个属性里，轮询到的状态会
把探测器覆盖掉；而当状态还没到时，`advise()` 会自己去问探测器：
那就是在界面线程上发一个 Praat 脚本（几百毫秒，并且会关掉用户开着的
菜单）。

改动：探测器与状态分开存放，并且明确告诉建议器"悬停路径不许自己去问
探测器"。状态由后台轮询提供，缺席时只是少一句上下文。

## 5. 还剩下什么慢

诚实地说，这几处没有解决：

1. **可及性树遍历**（`find_all` 178 ms、`tree` 86 ms）。这是 UIA 本身的
   成本。改造后它只在很少的场合发生（弹窗兜底、画布兜底），但它依然是
   整个系统里最贵的单个操作。下一步的方向是换 Win32 消息读取菜单项，
   或者干脆不要菜单项的完整列表。
2. **抓屏**（`canvas.capture` 34 到 39 ms）。只有"看图说话"这条路线需要它，
   而且它不在悬停的关键路径上（异步做）。
3. **深度探测的脚本往返**（约 290 ms）。它必须发脚本给 Praat，Praat 必须
   执行它，这个时间省不掉，只能更少地发。
4. **端到端延迟的 95 % 仍然是等待**。299 ms 里，280 ms 是停顿本身，
   剩下的是轮询节拍（47 ms）。要再快，就只能缩短停顿或者缩短轮询间隔，
   而这两者都会换来更多的误触发或者更多的 CPU。
5. **偶发的长尾**。测到过偶发的一次端到端 2.6 秒（改之前）：原因是那一
   次深度探测的脚本正好在 Praat 里执行，所有对 Praat 窗口的读取都要排队。
   守卫已经把这个概率压到很低（改之后同一批测量里的最大值是 346 ms），
   但它没有归零。

## 6. 复现

```bash
# 改之前的实现（同一套工具）
python prototypes/v1/experiments/perf_probe.py --legacy --out prototypes/v1/experiments/perf_baseline.json

python -m unittest discover -s tests
```

工具会移动鼠标，跑完会把指针放回原来的位置。测量期间不要用同一个桌面
上的别的程序动鼠标：被打断的轮次会被工具丢掉并报告出来。

结果文件：

* `prototypes/v1/experiments/perf_baseline.json`：改之前的实现（`--legacy`）
* `prototypes/v1/experiments/perf_after.json`：改之后的实现
* `prototypes/v1/experiments/perf_ftr_after.json`：改之后的误触发率
* `prototypes/v1/experiments/perf_ftr_before320.json`、`perf_ftr_before280.json`：
  改之前的误触发率（各自的停顿值）

## 7. 行为有没有变

没有。以下几条是硬性要求，改造后逐条复核过：

* 菜单开着的时候，教练**不会**把它关掉（弹窗项走弹窗自己的树，不用
  命中测试）。
* 教练**不会**抢焦点（命中测试与深度探测都有前台守卫）。
* 别的程序在前台时，深度探测**不发**脚本。
* 停顿时间**没有调长**（320 ms → 280 ms，见 4.4，误触发率已实测）。
* 卡片出现的判据仍然是"指针停在同一个控件上"，换控件就重新计时。
